# Закупки ФС-1 — слайсы реализации

Источник правды по **очереди работ**. Архитектура и запреты — `.cursor/rules/procurement.mdc` и `procurement-requests.mdc`. SQL-детали таблиц — постановка §6; этот файл не дублирует DDL.

**Как работаем.** Один слайс = один проход (PR / сессия), в конце есть что ткнуть руками. Не начинаем следующий, пока предыдущий не закрыт по «Готово когда». UI-слайсы: debounce 350, стабильные query keys, селекторы стора, колонки Table не в JSX. Клиент **не шлёт status**.

**Вне этой очереди:** ФС-2…8 (договоры как отдельный процесс, исполнение, акты, NDA, инвестпрограмма). Слайс 12 только **создаёт** документ-заглушку из запроса; карточку договора ФС-2 не рисуем.

Тезис не мигрируем: пустая база, номера с SEQUENCE.

**Сейчас в коде:** S0–S12 (меню, SQL, API черновика, реестр/форма, источник закупки и ВИ-2, смена привязки и журнал, утверждение ВИ-4, ведущий ОУП, поставщики, КП, сравнение/НМЦД/выбор, согласование после проработки, способ закупки). SQL и RBAC прогнать вручную в DBeaver — CI не мигрирует. Для уже существующей базы: `docs/procurement-requests-s5.sql`, затем `docs/procurement-requests-s6.sql`, `docs/procurement-requests-s7.sql` + повтор `docs/procurement-rbac.sql`, затем `docs/procurement-requests-s9.sql` (справочник НДС), затем `docs/procurement-requests-s10.sql` (снимок НМЦД), затем `docs/procurement-requests-s11.sql` (тип `purchase_request_agreement` и маршрут). Новых SQL для S8 и S12 нет: пороги способов уже в S1, `purchase_request_suppliers` уже в S1.

## S0. Платформа: право и вход

**Зачем.** Без секции Guarded-роут и меню не повесить; иначе UI соберут на `contracts.list`.

- `SECTIONS.PROCUREMENT_REQUESTS` (`procurement.requests`) зеркально backend + frontend.
- Seed `sections` + выдать read/edit роли инициатора (админка / SQL seed).
- Пункт меню «Закупки → Запросы» в `layouts/data.tsx` **выше** «Реестр оценок».
- Роут `/procurement/requests` с `<Guarded>` (страница-заглушка допустима).

**Готово когда:** пользователь с правом видит пункт; без права — 403/скрыто.

## S1. Данные ФС-1

**Зачем.** CI миграции не гоняет — как Гант и оценки: скрипт в `docs/` + Drizzle в `schema.ts`. Все таблицы ФС-1 сразу: Tezis пустой, дешевле один прогон, чем шесть.

- `apps/backend-nest/docs/procurement-requests.sql`: sequence `purchase_request_number_seq`; таблицы `purchase_requests`, `purchase_request_suppliers`, `purchase_quotes`, `purchase_quote_payment_terms`, `purchase_request_selection_reasons`, `purchase_method_thresholds`; справочники `ref_purchase_selection_reasons`, `ref_purchase_methods` (+ FK способа на запрос).
- Индексы из постановки: unique `number`; `status`, `project_id`, `income_contract_id`, `is_urgent`.
- Сид причин (ЗАП-23) и порогов БП-1 с `vat_base = net` (шов ОВ-46).
- Зеркало таблиц в `schema.ts`. `updated_at` для 409.

**Готово когда:** скрипт прогнан вручную; `GET` ещё нет — это норма.

## S2. Черновик: API (ВИ-1 без UI)

**Зачем.** Правила на сервере (ЗАП-2): карточку создают и без формы.

- Модуль `modules/procurement-requests/`: module, controller, service, dto, `domain/purchase-request.transitions.ts` (пока только создание → `draft`), `domain/purchase-request.policy.ts` (черновик пишет инициатор-владелец).
- `POST /api/procurement/requests` — номер из sequence, БП-20, срок ≥ даты запроса → 422, список полей в 400.
- `GET /` список `{ data, total }` + `parsePagination`; фильтры status/project/initiator; срочные можно уже `ORDER BY is_urgent DESC`.
- `GET /:id`, `PATCH /:id` — 403 чужой черновик; 409 если `updated_at` не сошёлся.
- Регистрация модуля в `app.module.ts` **до** Files catch-all.

**Готово когда:** curl/Postman: создать → номер 1, 2; пустые обязательные → 400 с именами полей; дата в прошлом → 422.

## S3. Черновик: реестр и форма (первый сквозной экран)

**Зачем.** Первый видимый срез: инициатор живёт здесь.

- `procurementRequestQueryKeys` (`all` / `list(params)` / `one(id)`), api + hooks.
- Реестр: `REGISTRY_PATHS`, persist UI, debounce поиска 350, колонки из `*Columns.tsx` / `useMemo`.
- Пусто: «Запросов нет» + создать. Ошибка загрузки — повтор.
- Форма создания (обязательные помечены). Карточка: шапка номер+статус, блок реквизитов, PATCH не на каждую букву.
- `openFromRegistry` / Back со скроллом и фильтрами.

**Готово когда:** создать → номер в шапке → строка в списке; поиск не бьёт API на символ; F5 на списке держит фильтры; Back возвращает скролл.

## S4. Источник закупки и ВИ-2

**Зачем.** Бюджет закупки = пара доходный договор + этап, не новая сущность.

- `funding_source`: `income_contract` | `investment_program` | `budget` (обязателен).
- ВИ-2: «Создать на основании доходного» — сначала договор (из `contracts` с признаком/типом доходного), потом этап; без этапов — договор без `income_stage_id`.
- На черновике поля договора/этапа необязательны (ЗАП-20).
- Для `investment_program` / `budget` — только источник, без фейковой сущности бюджета (ОВ-49).

**Готово когда:** путь «на основании» открывает форму с уже выбранным договором; договор без этапов сохраняется.

## S5. Смена привязки и журнал (ВИ-3, ЗАП-4…6)

- `PUT /:id/income-contract` в **одной транзакции** (пока каскад только сам запрос — порождённых документов ещё нет).
- Журнал действий: было / стало / кто / когда. Без-3: любая мутация в журнал.
- Право `procurement.correction` завести в `SECTIONS`, но ветку «после заключённого расходного» включить, когда появится ФС-2; до этого — меняет инициатор или ОУП.

**Готово когда:** смена этапа пишется в историю на карточке; без комментария на служебной ветке — 400 (когда ветка живая).

## S6. Утверждение запроса (ВИ-4, ЗАП-8, БП-32)

**Зачем.** Не свой workflow: entity type `purchase_request` в approvals.

- `POST /:id/submit` → `pending_approval`, старт процесса. 409 если не `draft`.
- Сид маршрута: решение принимают РП проекта **или** начальник подразделения-инициатора; техприёмщик — уведомление, без задачи.
- Событие approvals → статус: утвердить → `in_elaboration` + задача руководителю ОУП; отклонить → `rejected`; вернуть → `draft`.
- Если источник доходный и договор/этап пусты: «Утвердить» недоступно, пока утверждающий не заполнит; отклонить/вернуть — можно. Заполнение = та же запись журнала, что ВИ-3.
- UI: кнопка «Отправить»; на карточке `ApprovalPanel`; действия «Утвердить / Отклонить / Вернуть».

**Готово когда:** инициатор отправил → у РП (или руководителя инициатора) задача согласования; утверждение без доходного **договора** при источнике доходный невозможно (пустой этап не блокирует); возврат снова даёт править черновик.

Сиды: `docs/procurement-requests-s6.sql` (тип `purchase_request`, маршрут `purchase_request_vi4`, шаг `owner_or_head` / `any`). Задачу «назначить ведущего ОУП» после утверждения создаёт handler в S7 (право `procurement.lead`), не `initiator_head`.

## S7. Ведущий ОУП (ЗАП-9)

- `POST /:id/lead` — только руководитель ОУП, статус `in_elaboration`.
- До назначения `lead_manager_id` пустой: сотрудник ОУП карточку **не пишет** (policy).
- UI: действие «Назначить» на карточке / в задаче руководителя ОУП.
- Секция `procurement.lead` (edit). Обычный `procurement.requests` edit ведущего не назначает.

**Готово когда:** без lead PATCH проработки → 403; после назначения ведущий видит поля проработки.

Сиды: `docs/procurement-requests-s7.sql` (снимает on_complete `initiator_head`) + повтор `docs/procurement-rbac.sql`. После SQL перелогиниться, чтобы в правах появился `procurement.lead`.

## S8. Поставщики (ЗАП-15…19, БП-27)

- ПрИ-1.1: один метод партнёра «флаги для закупки» (одобрен, категория, дата переоценки, блок по `project_id` запроса). Не N+1.
- `POST /:id/suppliers` — `warning_snapshot` jsonb на момент добавления; 409 если уже есть.
- Предупреждение на UI, добавление не запрещать.
- ЗАП-19: кнопка «завести контрагента» → существующий create партнёра, затем add в запрос.
- Переход на карточку партнёра.

**Готово когда:** в строке подбора видны A–D и блок по проекту; нет в реестре → создали партнёра → он в запросе и в `/partners`.

## S9. Коммерческие предложения (ЗАП-21, БП-31)

- `POST /:id/quotes`, `PATCH /quotes/:quoteId`.
- Строки оплаты, сумма долей = 100 → иначе 422. Аванс без days/day_kind (БП-16).
- Файл КП через files-service (`entityType` `purchase_quote` → `/purchase_quotes/:id/files`).
- 409: по поставщику уже есть КП. 403: не `in_elaboration` или не ведущий. Policy, не `@RequirePermission(edit)`.
- Ставка НДС из справочника `ref_vat_rates` (`docs/procurement-requests-s9.sql`), не числом в форме. `GET catalog/vat-rates`.

**Готово когда:** два КП с разными условиями оплаты сохраняются; 99 % долей — 422; файл открывается с карточки.

## S10. Сравнение, НМЦД, выбор поставщика (ВИ-5 хвост, БП-33…35)

- Чистый `domain/nmcd.ts` + тесты на выброс 33 % и «осталось < 3».
- `POST /:id/price` — метод + note для `impossible`; в БД `initial_max_price` **и состав** (вошло / исключено / отклонение).
- UI сравнения: критерий × поставщик, лучшие подсвечены, база отклонения — экспертная цена.
- `POST /:id/supplier` — quoteId + ≥1 reasonCodes + optional note.
- БП-35: на карточке предупреждение (пн–пт). Confirm и **428** — на отправку к согласованию в **S11**, эндпоинта согласования здесь ещё нет.

**Готово когда:** рынок с выбросом показывает исключённые КП; < 3 после фильтра — 422; выбор без причины — 400; НМЦД после перезагрузки карточки та же.

## S11. Согласование после проработки

**Зачем.** Второй процесс approvals (не путать с ВИ-4). Статусы `in_agreement` → `agreed` (или назад в проработку со сбросом решений, БП-28 — способность движка).

- Кнопка «Отправить на согласование» только если НМЦД зафиксирована и поставщик выбран (уточнить policy в коде, не в форме в обход API).
- БП-35: confirm на отправку; без флага → **428**.
- Второй entity type `purchase_request_agreement` + `POST detail/:id/to-agreement` — ВИ-4 на `purchase_request` после approve лочит повторный старт.
- Предпросмотр объекта в списке задач (ЗАП-27) — если inbox approvals это умеет; иначе карточка + ссылка, предпросмотр отдельным микрослайсом.

**Готово когда:** после согласования статус `agreed`; способ закупки на этом экране **ещё скрыт**.

## S12. Способ закупки (ВИ-6, БП-1, БП-2, БП-36)

- `GET /:id/methods` — 409 если не `agreed`; в ответе допустимость и границы порога; сравнение через `vat_base` строки (ОВ-46).
- `POST /:id/method` — вне порога без `methodJustification` → 400; обоснование уходит согласующим отдельным пунктом (поле на карточке).
- UI отдельным шагом **после** `agreed`, не в блоке проработки.

**Готово когда:** сумма в «до 100 включительно» на 100_000 без НДС (при `net`); способ выше порога без текста не сохраняется.

## S13. Путь оформления (ВИ-7, ЗАП-12…14)

- `POST /:id/route` `{ kind, baseContractId? }`.
- `contract` / `tender` / `invoice` — создать запись-заглушку (для `contract` — минимальный `contracts` с переносом предмет/проект/доходный/этап/сумма/валюта) либо явный 501 на tender/invoice, если каркаса нет: **в слайсе решить одно** — заглушка в `contracts` для `contract`, для остальных 422 «не в версии» лучше, чем тихий noop.
- `amendment` / `order` — только `is_active` договор; неактивный → 422.
- Транзакция: документ + связь с запросом.

**Готово когда:** «Оформить → договор» открывает существующую карточку договора с данными запроса; ДС на неактивный — отказ. Полный ФС-2 (ДС/заказ как сущности) — следующая очередь, не этот слайс.

## S14. Цепочка происхождения (ЗАП-7, ПИ-1)

- `GET /:id/chain` — дерево одним запросом, без таблицы-кэша в БД.
- Блок на карточке запроса (и позже на порождённых документах).
- React Query: ключ `chain(id)`, пока открыта карточка.

**Готово когда:** с запроса клик в доходный договор и обратно; после S13 в цепочке виден расходный.

## S15. Реестр и полировка ФС-1

- Срочные: цвет + подъём в списке и в задачах (ЗАП-25).
- Настройка колонок пользователя (ЗАП-26) — user prefs, не таблица модуля.
- Файлы запроса в карточке (ПрИ-3).
- Policy `writableFields(status, role)` довести до всех полей (Без-1, БП-18).
- Чеклист quality-gate реестра (скролл, F5, смена page).

**Готово когда:** ФС-1 можно отдавать ОУП на UAT по ВИ-1…7 без ФС-2 в полном виде.
