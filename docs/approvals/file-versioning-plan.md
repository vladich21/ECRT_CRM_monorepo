# План: версионность документов согласования (Вариант X — эталон)

> Round-snapshot версии («Версия 1/2/3») на каноничном фундаменте: хранение файлов по id +
> версионная модель в общем модуле `files`. Заодно чинит латентный баг коллизии одноимённых файлов.
> Дата: 2026-06-17.

## 0. Контекст и корень проблемы

Текущая файловая система (`apps/backend-nest/src/modules/files/`):
- Физический путь: **`uploads/{entityType}/{entityId}/{originalName}`** (`files.service.ts:123,129`, `getFilePath:319`) — **секция и версия в путь НЕ входят**.
- Уникальный ключ в БД: `(entityType, tableId, documentSection, name)` (`files.service.ts:185`).
- Скачивание: `GET /files/:id` (авториз.) и `GET /files/public/:id` (подпись), плюс legacy `GET /:entityType/:entityId/:filename` (by-name).
- Используется **всеми** сущностями (договоры, партнёры, патенты, проекты).

**Блокер:** путь по имени ⇒ два файла с одинаковым именем (v1/v2 «Договор.docx») пишутся по одному пути ⇒ второй затирает первый физически. Хранить версии одноимённого файла нельзя без смены схемы хранения. (Это же — существующий латентный баг: одноимённые файлы в разных секциях уже коллизятся.)

## 1. Целевая модель

### 1.1 Хранение по непрозрачному id (фундамент)
- Новый физический путь: **`uploads/files/{fileId}/{originalName}`** (папка по UUID файла → коллизий имён нет, реальное имя сохраняется для отдачи).
- **Бэкомпат чтения:** `getFilePath(file)` сначала пробует id-path, при отсутствии — legacy `uploads/{entityType}/{entityId}/{name}`. Новые загрузки идут в id-path; существующие читаются по-старому. **Без принудительной миграции.**

### 1.2 Версионная модель в `files` (общая, переиспользуемая)
- `+ version int NOT NULL DEFAULT 1`
- `+ is_current boolean NOT NULL DEFAULT true`
- Уникальный индекс: `(entity_type, table_id, document_section, name, version)` (вместо текущего без version).
- Семантика: набор последней версии — `is_current=true`; `version` — номер раунда/снапшота.

## 2. Механика согласования (round-snapshot поверх 1.x)

- **Создание:** файлы из модалки запуска → `version=1, is_current=true, document_section='approval'`.
- **Активный раунд:** панель документов read-only (как сейчас).
- **Возврат на доработку → повторная отправка (твой сценарий):**
  «Отправить повторно» открывает **модалку**, предзаполненную текущими (`is_current`) документами как черновик набора `version=N+1`:
  - инициатор **заменяет** нужные файлы (и/или добавляет);
  - на подтверждении backend создаёт набор `version=N+1` (неизменные — физическая копия под новым id; заменённые — новые файлы), старую версию помечает `is_current=false`; затем выполняет resubmit;
  - в ленту — события `resubmitted` (есть) + `file_replaced` (заготовка в EVENT_LABEL уже есть).
- **Панель «Документы»:** группировка `section='approval'` по `version` → блоки **«Версия N»**. Текущая (`is_current`) — редактируема инициатором на доработке; прошлые — read-only архив (только скачивание).

## 3. Изменения — Backend

1. **schema.ts** `files`: `+ version`, `+ is_current`; новый уникальный индекс (с `version`).
2. **SQL** `scripts/approvals/07_file_versions.sql`: добавить колонки, `DROP` старый unique + `CREATE` новый (с version), backfill `version=1`/`is_current=true`. Применить к `pmdb_stage`.
3. **files.service.ts:**
   - `saveFile`/upload → id-based путь (`uploads/files/{id}/{name}`); запись `version`, `is_current`.
   - `getFilePath`/`resolvePublicFileDownload` → фолбэк id-path → legacy.
   - upload принимает `version` (по умолчанию 1) и помечает `is_current`.
   - новый метод `snapshotFilesToNextVersion(entityType, entityId, section, replacements[])` — физически копирует неизменные, создаёт заменённые, ставит version+1/is_current.
   - `mapRow` → отдавать `version`, `is_current`.
4. **approvals engine `resubmit`:** оркестрировать снапшот версии (или отдельный endpoint `POST /approvals/processes/:id/resubmit` принимает список замен) + запись события `file_replaced`.
5. **getFilesByEntity** → `MyFile` получает `version`, `is_current`.

## 4. Изменения — Frontend

1. `types/files.ts` `MyFile`: `+ version`, `+ is_current`.
2. **ApprovalDocuments:** группировка по `version`, блоки «Версия N (текущая/архив)»; скачивание (готово, blob); удаление/замена — только в текущей версии и только инициатору на доработке.
3. **Resubmit:** заменить `Popconfirm` на **модалку** с предзаполненными документами и заменой по каждому файлу → resubmit с заменами.
4. **Лента:** событие `file_replaced` уже поддержано (`EVENT_LABEL`).

## 5. Бэкомпат и миграция

- Существующие файлы: backfill `version=1, is_current=true`; физически остаются по старому пути → читаются через фолбэк. Новые — id-path. (Опц. позже — фоновая миграция старых в id-path.)
- Другие сущности: получают `version=1/is_current=true`, их UI **не меняется** (показывают всё, `is_current` не фильтруют). Изменения колонок аддитивны (default) — не ломают.
- Уникальный индекс пересоздаётся на `files` (на стейдже данных немного — безопасно; на проде — `DROP/CREATE INDEX`).

## 6. Риски

- **Общий files-модуль** используется всеми сущностями → риск регресса. Митигировать: не менять их поведение (version по умолчанию, фолбэк путей), прогнать build + smoke загрузки/скачивания у одной не-approval сущности (например contract «Файлы»).
- **legacy by-name serve** (`:entityType/:entityId/:filename`) для id-файлов не сработает (нет уникальности по имени) — но новые файлы качаются через `/files/:id` (мы уже так делаем в ApprovalDocuments). Проверить, где UI ещё использует by-name URL (`f.url`/serveFile) и при необходимости перевести на `/files/:id`.
- **Дублирование физических файлов** на каждую версию — рост хранилища (приемлемо для документов; оптимизация ссылками — позже).

## 7. Фазы

- **F-V0** — схема + миграция (колонки, unique index, backfill) на `pmdb_stage`.
- **F-V1** — files: id-based storage + фолбэк чтения + upload version/is_current; smoke (загрузка/скачивание у contract «Файлы», не сломали).
- **F-V2** — `snapshotFilesToNextVersion` + resubmit-снапшот (backend) + событие `file_replaced`.
- **F-V3** — frontend: блоки «Версия N» + resubmit-модалка с заменой.
- **F-V4** — проверки: build + smoke сценария (создать с v1 → доработка → версия 2 → блоки; прошлые версии read-only + скачиваются).

## 8. Открытые вопросы (решить на входе в фазу)
1. Неизменные файлы при снапшоте — **дублировать физически** (проще) или **ссылаться** (экономия места)? Рекоменд. для v1 — дублировать.
2. Замена в текущей версии во время доработки — **через панель** (как сейчас, upload в revision) или **только в resubmit-модалке**? Рекоменд. — resubmit-модалка (соответствует «дублировать→заменить→отправить»).
3. Прошлые версии — только просмотр/скачивание (да).
