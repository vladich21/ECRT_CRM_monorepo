# Анализ стека и устойчивости под нагрузкой

Документ объединяет выводы из обсуждения «NestJS — уродливый монстр или энтерпрайз?» (чат.md), статьи про фулстак-разработку (statya.md) и аудит вашего монорепозитория (React, TanStack Query, NestJS, Drizzle).

---

## 1. Сводка по чату и статье

### Из чата про NestJS

- **Критики Nest:** избыточная сложность, «как Spring в JS», DI в JS не обязателен, конфликты зависимостей, тяжёлый node_modules, сложная отладка из-за декораторов и .map-файлов. Часть команд после лет использования перешла на **Fastify + TypeScript + DDD** без Nest.
- **Сторонники Nest:** единый стандарт и архитектура, быстрая настройка валидации/сериализации/документации, удобный DI и тестирование, проще онбордить новых людей.
- **Важно:** Nest под капотом использует Express или Fastify — то есть это прослойка над HTTP. Производительность в первую очередь упирается в **вашу логику, запросы к БД и I/O**, а не только во фреймворк.

### Из статьи про фулстак

- **Бэкенд:** Express — для малых/средних проектов, **Fastify — если важна производительность**, NestJS — для больших команд и жёстких соглашений. Не усложнять без необходимости.
- **Базы:** PostgreSQL по умолчанию, индексы и пагинация обязательны, N+1 избегать, кэш (Redis) для тяжёлых/частых запросов.
- **Масштаб:** хорошо оптимизированный монолит на скромном железе может держать тысячи RPS; начинать с монолита, микросервисы — при явной необходимости.
- **Кэш:** Redis как стандарт, продуманная инвалидация (TTL, по событию).

## 2. Оценка вашего стека под большим потоком нагрузки

| Слой              | Технология      | Вердикт под нагрузкой |
|-------------------|-----------------|------------------------|
| Фронтенд          | React + Vite    | ✅ Норм: Vite быстрый, React типичный выбор. |
| Запросы/кэш UI   | TanStack Query  | ✅ Плюс: кэш запросов, дедупликация, меньше лишних запросов к API. |
| Бэкенд            | NestJS + Express| ⚠️ Приемлемо: Express под капотом, узкое место обычно не в нём, а в БД и отсутствии пагинации/кэша. |
| БД                | Drizzle + PG    | ✅ Хорошо: лёгкий слой, параметризованные запросы, типобезопасность без тяжёлой магии ORM. |
| Кэш/очереди       | Нет             | ❌ Нет Redis/очередей — при росте нагрузки и повторяющихся запросах будет лишняя нагрузка на БД. |

**Итог:** Стек в целом выдерживает высокую нагрузку **при условии**, что:

1. Все списки ограничены (limit/offset или cursor) и не тянут всю таблицу.
2. Тяжёлые или частые чтения кэшируются (Redis или in-memory где уместно).
3. Есть индексы под реальные запросы и нет N+1.
4. Тяжёлые операции (экспорт, отчёты, рассылки) вынесены в фоновые задачи (очереди).

Раньше в коде были критические места без пагинации; для основных списков это **уже исправлено** (см. ниже).

## 3. Что улучшить уже сейчас (конкретно по коду)

### 3.1. Пагинация и ограничение выборок — статус

| Эндпоинт | Статус | Реализация |
|----------|--------|------------|
| `GET /api/users` | ✅ **Решено** | `limit`/`offset` (дефолт 50, макс. 100), ответ `{ data, total }`. См. `users.controller.ts`, `users.service.ts`, `common/pagination.ts`. |
| `GET /api/contracts` | ✅ **Решено** | `limit`/`offset` в контроллере и сервисе, выборка с `.limit()`/`.offset()`. |
| `GET /api/patents` и `GET /api/patents/deleted` | ✅ **Решено** | `limit`/`offset`, ответ `{ data, total }`. На фронте РИД — серверная пагинация с total. |
| `GET /api/comments` | ⚠️ Без cap | Сейчас отдает все комментарии по сущности. Если когда-то комментариев станет много, стоит добавить cap/пагинацию. |
| `GET /api/contract-types` | ⚠️ Без cap | Справочник, обычно небольшой — приемлемо. При желании можно добавить явный `.limit(500)` для защиты. |

Итог: списки users, contracts, patents и comments **больше не тянут всю таблицу** — запрашиваются только страницы (limit/offset). Детали контракта и тесты: `apps/backend-nest/docs/PAGINATION.md`.

### 3.2. Кэширование (medium-term)

- **Справочники:** `contract-types`, `patent_application_areas`, типы партнёров, статусы и т.п. меняются редко — идеально кэшировать в памяти (in-memory в Nest) или в Redis с TTL 5–15 минут.
- **Списки:** кэшировать полные списки не стоит (часто устаревают), а вот **отдельные сущности по id** (контракт, патент, пользователь) после первого чтения можно кэшировать на короткий TTL (1–5 мин), если они часто запрашиваются.
- **Статья и чат:** Redis как стандарт для кэша и для распределённого rate limiting при нескольких инстансах.

**Уже сделано:** справочник договоров (GET /contracts?for_reference=1) возвращает **все** договоры без лимита и кэшируется in-memory в `ContractsService` на 10 мин; кэш сбрасывается при создании/обновлении/удалении договора. Фронт запрашивает справочник через `getContractsForReference()`; повторные запросы отдаются из кэша.

Практичный порядок: сначала in-memory кэш для мелких справочников в одном инстансе; при горизонтальном масштабировании или необходимости разделять кэш между инстансами — Redis.

### 3.3. Индексы БД

- Уже обсуждалось: индекс по `users.email`, составной по `auth_codes(user_id, type, created_at)`.
- Нужно проверить под реальные запросы: `contracts` (фильтр по `partner_id`, сортировка по `number`), `patents` (по проекту/договору, `is_deleted`), `comments` по `entity_type` и `entity_id`. При необходимости добавить индексы в схему Drizzle и миграции.

### 3.4. Тяжёлый I/O и фоновые задачи

- **Файлы:** загрузка/отдача через Nest — без изменений логики; при росте объёма стоит хранилище (S3-совместимое) и отдача через CDN/прокси.
- **Экспорт (Excel и т.д.):** если делается синхронно в HTTP-запросе — при большом потоке лучше выносить в очередь (Bull/BullMQ + Redis), отдавать клиенту «задача создана», а результат — по готовности (файл или ссылка).

### 3.5. NestJS: менять или нет?

- **Из чата:** часть команд ушла с Nest на Fastify из-за сложности и зависимостей; другие считают Nest удобным для стандартизации.
- **Из статьи:** Nest — для больших команд и строгих соглашений; Fastify — когда важна производительность.

**Рекомендация для вашего проекта:**

- **Не переписывать бэкенд на Fastify сейчас.** Основной выигрыш под нагрузкой дадут пагинация, кэш, индексы и вынос тяжёлых операций в фоновые задачи. Смена Nest на Fastify даст прирост по RPS, но меньше, чем исправление «выбрать всё без limit».
- Оставить Nest разумно: уже есть модульная структура, валидация, гард авторизации, rate limit на auth. При росте команды единый стиль Nest может быть плюсом.
- Если позже появятся жёсткие требования к минимальной задержке (p99) или к количеству инстансов при ограниченном железе — можно рассмотреть переход на **Nest + Fastify adapter** (официальная поддержка) вместо переписывания на чистый Fastify.

### 3.6. Drizzle

- Drizzle не тянет в сторону «тяжёлого ORM»: запросы явные, N+1 контролируются вами, параметризация есть. Оставить как есть, следить за сложными `findAll` и джойнами — везде, где можно, использовать `limit`/`offset` и при необходимости кэш.

## 4. Приоритеты внедрения

| Приоритет | Действие | Зачем |
|-----------|----------|--------|
| 1         | Пагинация для `users`, `contracts`, `patents`, при необходимости для `comments` | Снижение объёма данных и времени ответа при росте таблиц и числа запросов. |
| 2         | Жёсткий limit (и при необходимости пагинация) для списков комментариев по сущности | Защита от запросов с огромным числом комментариев. |
| 3         | In-memory (или Redis) кэш для мелких справочников | Меньше обращений к БД на каждый запрос. |
| 4         | Проверка и добавление индексов под частые фильтры и сортировки | Стабильное время выполнения запросов при росте данных. |
| 5         | Вынос тяжёлых отчётов/экспортов в очередь | Чтобы синхронные запросы не блокировали воркеры при большом потоке. |
| 6         | (Опционально) Redis для rate limit и сессий при нескольких инстансах | Единый лимит и состояние при горизонтальном масштабировании. |

## 5. Краткий вывод

- **Стек (React, TanStack Query, NestJS, Drizzle) под большим потоком нагрузки выстоит**, если устранить «узкие места»: списки без лимитов, отсутствие кэша для справочников и тяжёлые синхронные операции.
- **NestJS** здесь не главный враг производительности; главное — проектирование запросов (пагинация, индексы) и кэширование. Решение из чата (переход на Fastify) оправдано при нежелании мириться со сложностью Nest, а не как единственный способ «спасти» производительность.
- Действия из раздела 4 дают **оптимальный и обоснованный** эффект: быстрые победы (пагинация, limit), затем кэш и индексы, затем фоновые задачи и при необходимости Redis и смена адаптера на Fastify внутри того же Nest.
